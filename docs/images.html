blog-nextjs · image pipeline

이미지는 어떻게 최적화되어
브라우저에 그려지는가

한 장의 이미지가 S3에 저장된 원본에서 출발해, Next.js를 거쳐 사용자의 브라우저에 그려지기까지의 전 과정을 그림으로 설명합니다. next/image가 뒤에서 무슨 일을 대신해 주는지 모르겠다면 여기서부터 보면 됩니다.

next/image AVIF · WebP srcset Amazon S3 rehype-image-size

00 개요

이미지는 보통 웹페이지에서 가장 무거운 자원입니다. 글자 한 페이지가 수십 KB라면, 사진 한 장은 수백 KB~수 MB입니다. 그래서 "원본을 그대로 내려주느냐"와 "상황에 맞게 가공해서 내려주느냐"는 체감 속도를 크게 가릅니다.

한 장의 이미지가 거치는 두 세계

🗄️ 저장소 (S3)

이미지 원본이 보관되는 곳. Obsidian에서 올린 스크린샷 등이 그대로 들어 있습니다. S3는 "파일을 안전하게 보관하고 HTTPS로 내어주는" 역할만 합니다 — 가공은 하지 않습니다.

⚙️ 최적화 계층 (next/image)

원본을 받아 브라우저·화면 크기에 맞게 가공하는 곳. 포맷을 바꾸고, 크기를 줄이고, 결과를 캐시합니다. 사용자가 실제로 받는 건 이 가공된 결과입니다.

핵심
사용자는 S3 원본을 직접 보지 않습니다. S3는 뒤편의 "원본 창고"이고, 사용자에게 닿는 건 next/image가 가공·캐시한 결과물입니다. 이 한 문장이 이 문서 전체의 뼈대입니다.

01 next/image가 대신해 주는 일

평범한 <img> 태그는 "이 URL의 파일을 그대로 받아와 그려라"가 전부입니다. next/image는 그 사이에 가공 단계를 끼워 넣습니다. 무엇을 해주는지 하나씩 봅니다.

① 포맷 변환 — 더 가벼운 형식으로 자동 변환

같은 사진이라도 파일 형식에 따라 용량이 다릅니다. 브라우저가 어떤 형식을 지원하는지 보고(Accept 헤더), 가장 가벼운 형식으로 바꿔 보냅니다.

브라우저가 받아들일 수 있는 가장 가벼운 형식을 자동 선택 — 사용자는 신경 쓸 필요 없음

② 리사이징 & srcset — 화면 크기에 맞는 크기로

휴대폰 화면(400px 폭)에 4000px짜리 원본을 통째로 내려보내는 건 낭비입니다. next/image는 여러 크기 버전을 만들어 두고, 브라우저가 자기 화면에 맞는 가장 작은 버전을 고르게 합니다. 이 "크기 후보 목록"이 srcset입니다.

서버가 강제하지 않고, 브라우저가 자기 상황에 맞는 후보를 알아서 고름

③ 지연 로딩 & 레이아웃 흔들림(CLS) 방지

🐢 지연 로딩 (lazy loading)

화면 밖에 있는 이미지는 스크롤이 닿기 전까지 아예 안 받습니다. 글 맨 아래 이미지 때문에 첫 화면이 느려지는 일이 없어집니다.

📐 CLS 방지

이미지가 들어올 자리(가로·세로 비율)를 미리 비워둡니다. 안 그러면 이미지가 늦게 도착할 때 아래 글자들이 갑자기 밀려나는 현상(레이아웃 흔들림)이 생깁니다.

전제 조건
CLS 방지는 이미지의 실제 크기를 미리 알아야 가능합니다. 그런데 마크다운으로 쓴 이미지(![](url))에는 크기 정보가 없습니다. 이 블로그가 이 문제를 어떻게 푸는지는 2-①에서 다룹니다.

④ Blur Placeholder — 로딩 중 흐릿한 미리보기

이미지가 도착하기 전, 빈 회색 대신 원본을 아주 작게 줄인 흐릿한 썸네일을 먼저 깔아둡니다. 색·구도가 어렴풋이 보여 "곧 이런 그림이 온다"는 느낌을 줍니다. (velog·Medium에서 보던 그 효과)

원격 이미지는 직접 만들어야 함
로컬 이미지는 next/image가 blur를 자동 생성하지만, S3 원격 이미지는 안 됩니다. 그래서 빌드 타임에 rehype-image-size가 16px webp 썸네일(~130 byte)을 만들어 blurDataURL로 주입합니다(2-①과 같은 자리).

02 S3 원본 → 브라우저까지의 전 과정

이제 한 장의 이미지가 저장에서 화면까지 어떤 순서로 흘러가는지 따라가 봅니다. 크게 빌드할 때 한 번, 그리고 사용자가 페이지를 열 때마다 두 시점으로 나뉩니다.

빌드 타임 (배포 시 1회) 요청 타임 (방문마다) S3 접근 (캐시 미스 시만)

① 빌드 타임 — 이미지 크기를 미리 알아낸다

마크다운 이미지에는 크기 정보가 없다고 했습니다(1-③). 그래서 이 블로그는 빌드할 때 rehype-image-size 플러그인이 S3의 각 이미지에 실제로 접속해 가로·세로 크기를 측정하고, 그 값을 HTML에 박아 넣습니다. 덕분에 CLS 방지가 가능해집니다. 같은 자리에서 blur 썸네일(16px webp)도 함께 생성해 주입합니다.

왜 빌드 타임에?
사용자가 페이지를 열 때마다 크기를 재면 매번 느려집니다. 배포할 때 딱 한 번 측정해서 결과를 HTML에 저장해 두면, 이후 모든 방문자는 추가 비용 없이 그 값을 씁니다. (측정 실패 시엔 16:9 기본값으로 폴백)

② 요청 타임 — 방문자가 페이지를 열 때

  1. 브라우저가 이미지를 요청

    HTML 안의 이미지 태그는 S3 주소가 아니라 /_next/image?url=...&w=1080&q=75 형태의 Next.js 프록시 주소를 가리킵니다. 브라우저는 이 주소로 요청합니다.

  2. Next.js가 캐시를 확인

    "이 URL + 이 크기 + 이 품질" 조합을 전에 만든 적 있나? 있으면(캐시 히트) 즉시 돌려줍니다 — S3는 건드리지도 않습니다.

  3. 없으면 S3에서 원본을 가져와 가공

    처음이면(캐시 미스) S3 원본을 한 번 fetch → 브라우저에 맞는 포맷(AVIF/WebP)으로 변환 → 요청된 크기로 리사이즈 → 결과를 캐시에 저장합니다.

  4. 브라우저가 받아 화면에 그림

    가공된 가벼운 이미지가 도착하면, 빌드 때 잡아둔 자리에 정확히 끼워 넣어 렌더링합니다. 레이아웃이 흔들리지 않습니다.

캐시 히트 vs 미스 — 무엇이 다른가

✅ 캐시 히트 (대부분의 방문)

브라우저 → Next 캐시 → 끝. S3 접근 0회, 변환 0회. 가장 빠른 경로입니다. 인기 글의 이미지는 거의 항상 이 경로를 탑니다.

⏳ 캐시 미스 (그 이미지의 첫 방문자)

브라우저 → Next → S3 fetch + 변환 → 캐시 저장 → 응답. 첫 한 명만 약간 느리고, 그 결과를 다음 사람들이 재사용합니다.

캐시는 누가 공유하나 — 사용자별이 아니다

흔한 오해: "캐시는 내 브라우저에만 있는 것 아닌가?" 아닙니다. /_next/image의 변환 결과는 서버(또는 CDN) 한곳에 저장되어 모든 방문자가 공유합니다. 캐시를 찾는 열쇠(키)에 사용자 정보가 들어가지 않기 때문입니다.

"A가 A1 이미지를 받으면, TTL 안에서는 B·C도 같은 캐시를 쓴다" — 첫 한 명만 변환 비용을 치름

Vercel 주의 — 지역별 캐시 분리
이 블로그는 Vercel 배포라 최적화 캐시가 Edge Network(CDN)에 저장됩니다. 전역 공유가 기본이지만, Vercel은 엣지 로케이션(지역)별로 캐시가 나뉩니다. A가 서울 엣지, B가 도쿄 엣지에 접속하면 B에겐 그 지역 첫 요청이라 미스가 날 수 있습니다 — 같은 지역 사용자끼리는 공유됩니다.

캐시 수명(TTL) — 얼마나 오래 살아 있나

캐시된 이미지는 영원히 살지 않습니다. 만료 시간(TTL)이 지나면 버려지고, 다음 요청 때 S3에서 다시 받아 재변환합니다. 만료는 이렇게 정해집니다:

만료 공식
TTL = max( minimumCacheTTL 설정값 , S3가 준 Cache-Control 값 ) — 둘 중 큰 쪽을 채택
요소이 블로그 값비고
minimumCacheTTL2,678,400초 (31일)next.config.mjs에 명시
S3 Cache-Control없음S3 객체에 헤더 미설정
→ 실제 적용 TTL31일큰 쪽 = 31일
왜 31일로 늘렸나
과거엔 설정이 없어 Next 15 기본값 60초가 적용됐습니다. 60초면 1분만 지나도 만료라, 트래픽 낮은 블로그에선 공유 캐시가 빛을 보기도 전에 사라져 거의 매번 S3 재요청·재변환이 일어났습니다. 블로그 이미지는 한 번 올리면 거의 안 바뀌므로 31일로 늘려 이 낭비를 없앴습니다.
대가 — 캐시 무효화 수단이 없다
Next.js는 이미지 캐시를 수동으로 비우는 기능을 제공하지 않습니다. 그래서 TTL을 길게 잡으면, 같은 URL의 이미지를 교체했을 때 최대 31일간 옛 이미지가 보일 수 있습니다. 단, 이미지를 바꾸며 S3 URL도 바꾸면 캐시 키 자체가 달라져 즉시 새 이미지가 반영됩니다(권장 방식).

📌 Next.js 16에서 기본값이 60초 → 4시간으로 바뀐 이유

같은 고민을 프레임워크 차원에서도 했습니다. Next.js 16부터 minimumCacheTTL 기본값이 60초에서 4시간(14400초)으로 상향됩니다. 공식 변경 사유는:

💸 재검증(revalidation) 비용 절감

Cache-Control 헤더가 없는 이미지(바로 이 블로그 같은 경우)는 60초마다 만료돼 원본 재요청·재변환이 반복됐습니다. Vercel에선 이 변환 횟수가 곧 과금이라, 짧은 TTL이 불필요한 비용을 유발했습니다.

🛡️ "안전한 기본값"으로 전환

대부분의 사이트가 TTL을 따로 설정하지 않습니다. 기본값이 60초면 모두가 무심코 비효율을 떠안는 셈이라, 프레임워크가 더 오래 가는 기본값을 주는 쪽으로 방향을 바꿨습니다.

요약하면 "짧은 TTL은 곧 반복 변환 = 반복 비용"이라는 깨달음입니다. 우리가 31일로 늘린 것과 정확히 같은 동기이며, Next 16은 그 방향을 기본값으로 끌어올린 것입니다. (이 블로그는 15.3.8이라 직접 설정으로 먼저 적용했습니다.)

03 이 블로그의 실제 구현

위 개념들이 코드에서 어디에 들어 있는지 짚어 둡니다.

🧩 AnimatedImage.tsx

모든 본문 이미지를 감싸는 컴포넌트. 주입된 width/height·sizes·blurDataURL을 넘겨 최적화를 켭니다. 첫 이미지엔 priority, 나머진 스크롤 등장 애니메이션.

크기 정책: width:100% + maxWidth=원본px → 작은 이미지는 원본 크기 유지, 큰 이미지만 본문폭으로 축소.

📏 rehype-image-size.mjs

빌드 타임 플러그인. probe-image-size로 S3 이미지 실제 치수를 측정(실패 시 1920×1080 폴백)하고, sharp로 16px webp blur 썸네일을 생성해 함께 주입.

⚙️ next.config.mjs

remotePatterns에 S3 버킷 등록(이 도메인만 /_next/image가 가공). 포맷은 Next 기본값(AVIF/WebP), 캐시 minimumCacheTTL=31일.

크기 정책 — 피해야 할 함정
style에 width:"auto"를 쓰면 안 됩니다. 고DPR(레티나·DevTools Responsive) 화면에서 표시 크기가 1/DPR로 축소되는 버그가 있습니다(예: 279px → DPR 2에서 112px). 반드시 width:"100%"(공식 권장) + maxWidth로 원본 상한을 줍니다.
참고
과거엔 unoptimized로 최적화를 끄고 원본을 그대로 내보냈지만, 지금은 위 구성으로 최적화가 켜진 상태입니다.

04 S3는 무엇을 하고, CloudFront는 왜 안 붙였나

마지막으로 저장소 쪽 이야기입니다. "S3에 CloudFront(CDN)를 붙이면 더 빠르지 않나?"라는 흔한 질문에 답합니다.

S3가 하는 일 / 안 하는 일

기능S3 직접 접근설명
파일 저장 · HTTPS 서빙✅S3의 본업. 원본을 안전하게 보관·전달
포맷 변환 (AVIF/WebP)❌저장된 그대로 내보냄 — 가공은 next/image 담당
리사이징❌원본 크기 그대로
전 세계 엣지 캐싱❌서울 리전 단일 — 이게 CloudFront가 채워줄 자리

CloudFront를 붙이면 얻는 것 / 못 얻는 것

✅ 얻는 것

· 전 세계 엣지 캐싱으로 지연 감소
· S3 요청·전송(egress) 비용 절감
· 원본 버킷 비공개 + CDN 뒤로 숨김(OAC)

❌ 못 얻는 것

· 포맷 변환·리사이징은 CloudFront 단독으론 안 됨
· 그건 Lambda@Edge를 따로 붙여야 가능

왜 지금은 안 붙였나
개요에서 본 것처럼 사용자는 S3를 직접 보지 않습니다. 사용자에게 닿는 건 next/image가 변환·캐시한 결과이고, S3는 그 뒤의 원본 창고입니다. S3 앞에 CloudFront를 둬도 빨라지는 건 Next가 캐시 미스로 원본을 한 번 가져오는 순간뿐 — 엣지 캐싱이 가장 빛날 "사용자↔S3 직접 트래픽"이 거의 없습니다. 그래서 개인 블로그 규모에선 실익이 낮다고 판단했습니다.

참고로 이미지 저장소는 과거 Cloudflare Images를 썼으나 비용 문제로 S3로 이전했습니다.
