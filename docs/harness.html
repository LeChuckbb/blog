Harness Architecture

blog-nextjs 운영 하네스

블로그 운영의 네 영역 — 발행 · 검수 · 동기화 · 개발 — 을 얇은 에이전트(누가)와 도메인 스킬(어떻게)로 분리한 자동화 체계. 에이전트는 워크플로우 흐름만 들고, 도메인 지식은 전부 스킬에 산다.

1 설계 원칙

왜 둘을 나누는가 — 컨텍스트 낭비 방지 · 지식 재사용 · 유지보수 단위 분리

🪶 얇은 에이전트

역할 · 입출력 · 협업 프로토콜만 정의. "무엇을 하는지"는 알지만 "어떻게 하는지"는 스킬에 위임한다. 그래서 컨텍스트가 가볍고 교체가 쉽다.

→

📚 두꺼운 스킬

변환 불변식 · frontmatter 규칙 · SEO 검수 기준 같은 도메인 지식을 담는다. 여러 에이전트가 공유하고, 한 곳만 고치면 모두 반영된다.

3 도메인 스킬

에이전트가 끌어 쓰는 지식 — 규칙·불변식·자동화 스크립트

blog-content-authoring
frontmatter 필수 필드, slug 정규화, 시리즈 규칙, 위키링크·이미지 관례, 발행 체크리스트.
obsidian-sync
동기화 6대 불변식(코드블록 보호·2-패스 slug·파일명 키 등)과 변환 규칙.
+ references/transform-rules.md
blog-seo-audit
frontmatter↔posts.json↔본문↔출력물 경계면 교차 검수. 심각도 기준.
+ scripts/audit.js (자동 점검)
nextjs-blog-dev
정적 생성 불변식, MDX 플러그인 체인, SEO 출력 4곳 전파 규칙, Tailwind 관례.
obsidian-safe-delete 안전 규칙
Vault 파일 삭제·이동 시 macOS 휴지통으로. rm 금지. 원본을 다루는 모든 에이전트가 공유하는 안전망.
blog-harness  ·  오케스트레이터
라우팅 표 · 복합 요청 파이프라인 · 컨텍스트 확인(초기/후속/부분 재실행) · 에러 핸들링 · 테스트 시나리오. 이 하네스의 진입점.

4 복합 요청 파이프라인

여러 에이전트를 엮을 때 — 앞 산출물이 다음 입력으로 흐른다

"글 검수 후 발행" seo-auditor → content-publisher
"SEO 기능 추가 후 검수" code-developer → seo-auditor
"변환 버그 고치고 점검" sync-maintainer → seo-auditor
