blog-nextjs

Obsidian에서 작성한 마크다운을 자동으로 MDX로 변환해 게시하는 Next.js 15 정적 블로그입니다. Obsidian → Google Drive → 변환 스크립트 → MDX → 정적 페이지로 이어지는 완전 자동화 콘텐츠 파이프라인을 중심으로 설계되었습니다.

Next.js 15.3 App Router MDX 3.1 SSG Tailwind CSS 4 TypeScript

1개요

이 프로젝트가 풀어내는 핵심 문제와 설계 철학

블로그 글을 작성하는 곳(Obsidian)과 게시하는 곳(Next.js)을 분리하고, 그 사이를 변환 스크립트가 메꿉니다. 작성자는 평소처럼 Obsidian에서 노트를 쓰고, 파일은 Google Drive로 동기화되며, 빌드 시점에 변환 스크립트가 Obsidian 고유 문법을 MDX로 정리한 뒤 정적 페이지로 굳힙니다.

✍️ 이중 워크플로우

작성은 Obsidian(.md), 게시는 Next.js(.mdx). 변환 스크립트가 둘을 연결.

⚡ 정적 생성(SSG)

모든 포스트를 빌드 시점에 미리 생성. 빠른 로딩과 SEO 최적화.

🔄 자동 동기화

sync:watch로 파일 변경을 감지해 실시간 변환.

3전체 데이터 흐름

한 편의 글이 Obsidian 노트에서 웹 페이지가 되기까지

Obsidian에 글을 쓰면 — sync가 변환하고 → next가 정적 페이지로 굳혀 → 브라우저가 띄웁니다. 자세한 단계는 §7.

4md vs mdx — 왜 변환하는가

Obsidian은 .md로 쓰고, 스크립트가 .mdx로 바꾸는 이유

.md · Markdown

  • 순수 텍스트 마크업
  • 결과물은 HTML 문자열
  • React 컴포넌트 삽입 ❌
  • import / export ❌
  • <, { }가 그냥 문자
→

.mdx · Markdown + JSX

  • 마크다운 + React(JSX)
  • 결과물은 React 컴포넌트
  • <Mermaid /> 등 컴포넌트 삽입 ✅
  • import / export 실행 ✅
  • <, { }는 JSX로 해석 → 이스케이프 필요
변환하는 이유. .mdx라야 본문을 React 컴포넌트로 import해 Mermaid·코드복사 버튼 같은 인터랙션을 끼울 수 있습니다. 대신 <, { }가 JSX로 해석되므로 변환 단계에서 이스케이프가 필요합니다. (transform-obsidian.js)

gray-matter는 frontmatter를 파싱하지만 MDX와 무관 — transform-obsidian.js·tocUtil.ts가 씀. 빌드 때는 remark-frontmatter가 따로 또 처리합니다.

MDX 파이프라인 — remark → rehype 2단계

빌드 시 .mdx는 두 단계를 거쳐 HTML이 됩니다. remark가 마크다운 의미 구조를, rehype가 최종 HTML 표현을 다룹니다.

📝 remark 단계 (마크다운 AST)

frontmatter 제거 · GFM · Obsidian 콜아웃 · 강조 마커 · 목차. 의미 구조를 가공.

🎨 rehype 단계 (HTML AST)

Shiki 코드 하이라이팅 · 헤딩 앵커 ID · 이미지 크기 주입. 표현을 가공.

6스크립트 5개는 어떻게 도는가

npm run dev/build = sync 먼저 → next 나중. 5개가 2그룹으로 나뉩니다.

그룹 1(config·transform·reading-time)은 sync-content.js가 require → Next 시작 전 끝. 그룹 2의 rehype-image-size.mjs만 빌드 도중 따로 동작 — 같은 폴더라도 실행 주체가 다릅니다.

7동기화 시스템 상세

scripts/ 폴더 — 파이프라인의 심장 (역할 요약은 §3 참고)

7.1 · config.js — 경로 자동 감지

Vault 경로를 하드코딩하지 않고 환경변수 → macOS Google Drive → Windows → 프로젝트 상위 순으로 탐색합니다. 덕분에 환경(맥/윈도우, 로컬/Drive)이 달라도 같은 코드가 동작합니다.

경로용도

blog-content/drafts/작성 중인 글 (무시)
content/변환된 MDX (출력)
src/app/posts.json메타데이터 (출력)

7.2 · transform-obsidian.js — 문법 변환

Obsidian에서만 의미 있는 문법들을 MDX가 이해할 수 있는 형태로 바꾸거나 제거합니다.

함수변환 (Obsidian → MDX)
removeObsidianComments%% 주석 %% → 제거
removeBlockIds^블록ID → 제거 (코드블록 보호)
convertWikilinks[[파일|텍스트]] → [텍스트](/posts/slug)
processImages![](Attached file/x.png) → ![](/images/x.png)
normalizeCodeFenceLanguage``` mermaid → ```mermaid
escapeMdxSpecialChars<, { } 등 JSX 충돌 문자 이스케이프

frontmatter도 정규화합니다 — publish_date를 date로 통일하고, slug가 없으면 파일명에서 생성합니다 (소문자화·공백→하이픈·한글 유지). 예: "React Hooks 완벽 가이드.md" → react-hooks-완벽-가이드

주의 · 코드블록 보호. 블록 ID(^id)나 콜아웃을 제거할 때 코드 펜스 안의 내용은 건드리지 않도록 정규식이 라인 단위로 신중하게 매칭합니다.

7.3 · sync-content.js — 동기화 오케스트레이션

전체 흐름을 지휘합니다. 핵심은 2-pass 설계 — ① 먼저 게시 글의 slug 집합을 모은 뒤(위키링크 연결 대상 판별), ② 파일을 변환하며 메타데이터를 수집합니다. 결과는 content/*.mdx 파일과, 각 글의 slug·title·date·tags·description·readingTime·series를 담은 posts.json(날짜순)으로 출력됩니다.

8포스트 렌더링

src/app/posts/[slug]/page.tsx — 정적 페이지 생성과 동적 MDX import

  • 정적 생성 — generateStaticParams()가 posts.json의 모든 slug에 대해 페이지를 미리 생성 (dynamicParams=false → 미생성 slug는 404)
  • 동적 import — slug로 해당 .mdx를 컴포넌트로 불러와 <Post />로 렌더링
  • 조합 — 제목 + 시리즈 네비(SeriesNav) + 본문 + 목차 사이드바(TableOfContents)
SEO. 각 페이지는 JSON-LD 구조화 데이터를 함께 출력하고, 목차 사이드바는 1440px 이상 화면에서만 sticky로 표시됩니다.

9목차 생성 & 스크롤 추적

서버에서 트리를 만들고, 클라이언트에서 현재 위치를 강조

서버 — 헤딩 추출 후 트리 구성 (tocUtil.ts)

MDX에서 헤딩을 정규식으로 뽑아 # 개수로 레벨(h1~h6)을 정하고, 스택으로 부모–자식 관계를 추적해 중첩 트리를 만듭니다. ID는 github-slugger가 생성해 한글도 안전합니다 (예: "React 비교" → react-비교).

클라이언트 — 스크롤 위치 추적 (TableOfContents.tsx)

스크롤할 때마다 현재 위치 바로 위의 가장 가까운 헤딩을 찾아 해당 목차 항목을 활성화합니다. scroll 이벤트(passive)로 가볍게 처리하고, 동적 콘텐츠 높이도 250ms 간격으로 추적합니다.

11한글 폰트

3종 체계 — 본문(산세리프) + 인용(세리프) + 코드(모노). 본문은 layout.tsx의 localFont로 연동.

역할현재 폰트분류 · 성격
본문 · UIPretendard산세리프 — 획이 균일·깔끔, 화면 가독성 높음. 교체 대상.
인용 · 헤딩마루 부리세리프 — 획 끝 장식, 전통적·문학적. 유지.
코드D2Coding모노스페이스 — 동일 너비, 코드 정렬·가독성. 유지.

본문 폰트 교체 시 후보 조합

Pretendard 자리에 넣을 산세리프 1종만 고르면 됩니다(인용·코드는 유지). 제목과 본문은 같은 폰트를 쓰고 굵기·크기로 위계를 표현합니다.

성격추천 폰트비고
안정적·범용Noto Sans KR완성도 최고. Pretendard와 가장 유사.
기술적·현대적IBM Plex Sans KR개발 문서 같은 신뢰감, 영문과 통일감.
가볍고 친근Gothic A1가는 획·둥근 끝, 개인 블로그에 어울림.
깔끔·미니멀Nanum Barun Gothic나눔 고딕 개선판, 균형감 우수.

한글 타이포그래피 권장값

한글은 영문과 행간·자간·줄바꿈 기준이 다릅니다.

body {
  line-height: 1.7;            /* 한글 본문은 넓게 1.6–1.8 */
  letter-spacing: -0.01em;     /* 산세리프는 약간 좁게 */
  word-break: keep-all;          /* 한글 어절 단위 줄바꿈 */
}
h1, h2, h3 { line-height: 1.3; letter-spacing: -0.02em; }  /* 제목은 좁게 */
blockquote { line-height: 1.8; letter-spacing: 0; }        /* 인용은 넓게 */
교체 방법. layout.tsx의 폰트 import·설정만 바꾸고 variable명을 유지하면 globals.css(--font-sans)는 수정이 거의 필요 없습니다. Google Fonts 한글 폰트는 subsets: ["latin"]만 지정해도 한글이 자동 포함됩니다("korean" subset 없음).
