# blog-nextjs 운영 하네스 — 오케스트레이터

이 하네스는 블로그 운영 작업을 4개 전문 에이전트에 라우팅한다. 에이전트는 **흐름만** 담당하고, 도메인 규칙은 모두 스킬에 있다. 너(오케스트레이터)의 역할은 요청을 분류하고, 맞는 에이전트를 띄우고, 결과를 종합하는 것이다.

## Phase 0: 컨텍스트 확인 (항상 먼저)

1. `_workspace/` 존재 여부 확인:
   - 없음 → **초기 실행**
   - 있음 + 사용자가 부분 수정/보완 요청("그 부분만 다시", "보완") → **부분 재실행**(해당 에이전트만 재호출, 이전 산출물 읽혀 개선점 반영)
   - 있음 + 새 입력/주제 → **새 실행**(기존 `_workspace/`를 `_workspace_prev/`로 이동 후 진행)
2. 요청을 아래 라우팅 표로 분류한다.

## 라우팅 — 어떤 에이전트를 띄우나

| 요청 유형 | 에이전트 | 사용 스킬 | 실행 모드 |
|---|---|---|---|
| 글 작성·발행, frontmatter/메타 보강, 시리즈 묶기 | **content-publisher** | blog-content-authoring, obsidian-sync | 단일(필요 시 seo-auditor 선행) |
| SEO·콘텐츠 품질 검수, 메타 감사, 내부링크 점검 | **seo-auditor** | blog-seo-audit | 단일 또는 병렬(글별 팬아웃) |
| 동기화·변환 버그, sync 스크립트 수정·확장 | **sync-maintainer** | obsidian-sync | 단일 |
| 앱 코드 리팩토링·기능 개발, MDX/SEO 출력 로직 | **code-developer** | nextjs-blog-dev | 단일 |

**복합 요청**은 파이프라인으로 엮는다. 대표 흐름:
- **"글 검수 후 발행"**: seo-auditor(검수) → content-publisher(보강·발행). 검수 리포트를 발행 입력으로 전달.
- **"SEO 출력 기능 추가 후 검수"**: code-developer(구현) → seo-auditor(검수).
- **"변환 버그 고치고 영향받은 글 점검"**: sync-maintainer(수정) → seo-auditor(재검수).

**공유 안전 규칙 — `obsidian-safe-delete`**: 어느 에이전트든 Obsidian Vault 내 파일을 삭제·이동·정리할 때는 반드시 이 스킬을 사용한다(macOS 휴지통 이동). `rm` 절대 금지. content-publisher·sync-maintainer가 Vault 원본을 다루므로 이 하네스 전체의 필수 안전망이며, 별도 하네스가 아니라 blog-harness 구성원이다.

## 실행 모드 (하이브리드)

- **단일 작업**: `Agent` 도구로 해당 에이전트 1개 호출(`model: "opus"` 필수, `subagent_type`은 에이전트 이름).
- **병렬 검수**: 글이 많아 글별로 나눠 검수할 때 seo-auditor를 여러 개 `run_in_background: true`로 띄운 뒤 결과 종합. 단, 전체 일괄 검수는 `audit.js` 스크립트 한 번이 더 효율적이니 먼저 스크립트로 1차 진단.
- **파이프라인**: 복합 요청은 앞 에이전트 산출물(`_workspace/`)을 다음 에이전트 입력으로 넘긴다.

> 2명 이상이 실시간 토론·상호참조해야 하는 경우는 드물다. 이 하네스는 기본적으로 **서브 에이전트 + 파일 기반 전달**로 충분하다. 팀 통신(TeamCreate)이 정말 필요한 상황(상충 토론)이 아니면 서브 에이전트로 유지해 오버헤드를 줄인다.

## 데이터 전달 프로토콜

- **파일 기반**(기본): 중간 산출물은 `_workspace/{phase}_{agent}_{artifact}.{ext}`. 최종 산출물만 사용자 지정 위치에. `_workspace/`는 보존(사후 검증·부분 재실행용).
- **반환값 기반**: 서브 에이전트의 요약·핵심 결과는 반환 메시지로 메인이 수집.

## 에러 핸들링

- 에이전트 1회 재시도 후 재실패 → 해당 결과 없이 진행하되 **누락을 명시 보고**. 임의로 파일을 건드리지 않는다.
- posts.json↔content 불일치, 변환 경고 등은 **삭제·수정하지 말고 보고**(소스는 Vault 원본/스크립트). 상충 데이터는 출처 병기.
- Vault 파일 삭제·이동이 필요하면 반드시 `obsidian-safe-delete` 스킬. `rm` 금지.
- 환경 문제(`OBSIDIAN_VAULT_PATH` 미설정 등)는 코드 우회 말고 사용자에게 보고.

## 실행 후 (Phase 7 연계)

작업 완료 후 사용자에게 피드백 기회를 제공한다("결과에서 바꾸고 싶은 점이 있나요?"). 피드백 유형별 수정 대상:
- 결과물 품질 → 해당 도메인 스킬
- 에이전트 역할 → `.claude/agents/{name}.md`
- 워크플로우 순서 → 이 오케스트레이터 스킬
- 트리거 누락 → 해당 스킬 description

구조 변경 사유는 git 커밋 메시지에 남긴다(별도 이력 테이블은 유지하지 않음). 같은 피드백이 2회 이상 반복되거나 에이전트가 반복 실패하면 진화를 먼저 제안한다.

## 테스트 시나리오

**정상 흐름 (글 검수 후 발행):**
1. 사용자: "이번 글 SEO 점검하고 발행 준비해줘"
2. Phase 0: `_workspace/` 없음 → 초기 실행. 복합 요청(검수+발행)으로 분류.
3. seo-auditor 호출 → `audit.js` 1차 진단 → 리포트 `_workspace/01_seo-auditor_report.md`.
4. content-publisher 호출 → 리포트 입력받아 frontmatter/description 보강 → `pnpm sync` → 발행 체크리스트 검증.
5. 메인이 종합 보고 + 피드백 기회 제공.

**에러 흐름 (동기화 실패):**
1. 사용자: "동기화가 안 돼"
2. sync-maintainer 호출 → 원인 진단(경로 미감지면 환경 문제로 보고, 변환 버그면 재현→수정).
3. 환경 문제(VAULT_PATH 미설정)면 코드 수정 없이 사용자에게 설정 안내 보고.
4. 변환 버그면 1회 재시도 포함 수정 후 `pnpm sync` 재검증, 영향받은 글 범위 보고.
